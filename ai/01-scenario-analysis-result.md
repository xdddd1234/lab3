# Результат AI-аналізу сценаріїв UC-03

## 1. Що перевірялося

Проаналізовано чотири сценарії видачі книги з лабораторної №2:

- SC-01 — успішна видача.
- SC-02 — книга вже видана.
- SC-03 — неправильна дата повернення.
- SC-04 — незареєстрований читач.

Мета аналізу — знайти пропущені кроки, можливі суперечності та визначити учасників майбутніх sequence-діаграм.

## 2. Пропущені кроки та можливі проблеми

| Сценарій | Що потрібно врахувати |
|---|---|
| SC-01 | Перевірити читача, доступність книги та дату повернення перед створенням Loan |
| SC-02 | Після виявлення активної видачі не створювати новий Loan і не змінювати старий |
| SC-03 | Порівняти due_date з поточною датою видачі та повернути помилку |
| SC-04 | Якщо Reader не знайдено, припинити оформлення без створення Loan |

## 3. Запропоновані учасники

- **Бібліотекар** — актор, який оформлює видачу.
- **LibraryUI** — інтерфейс, через який вводяться дані.
- **LoanService** — компонент, який керує процесом видачі.
- **ReaderRepository** — доступ до даних Reader.
- **BookRepository** — доступ до даних Book.
- **LoanRepository** — доступ до даних Loan.

`LibraryUI`, `LoanService` та репозиторії є програмними компонентами, а не новими сутностями ER-моделі.

## 4. Запропоновані повідомлення

| Виклик | Призначення |
|---|---|
| `submitLoan(readerId, bookId, dueDate)` | Надіслати запит на видачу |
| `findReaderById(readerId)` | Перевірити, чи існує читач |
| `findBookById(bookId)` | Отримати дані книги |
| `findActiveLoan(bookId)` | Перевірити наявність активної видачі |
| `validateDueDate(dueDate, loanDate)` | Перевірити дату повернення |
| `createLoan(readerId, bookId, loanDate, dueDate)` | Створити запис Loan |
| `showError(message)` | Показати помилку |
| `showSuccess(message)` | Показати результат успішної видачі |

Це запропоновані назви операцій для моделі, а не підтверджені методи готової програми.

## 5. Комбіновані фрагменти

Для кожної діаграми можна використати `alt`:

- SC-01 — умови виконані / виникла помилка.
- SC-02 — активну видачу знайдено / не знайдено.
- SC-03 — дата неправильна / дата правильна.
- SC-04 — читача не знайдено / читача знайдено.

Також можна використати `opt` для показу повідомлення користувачу.

## 6. Топ-3 ризики

### Ризик 1 — Невідповідність Gherkin

Якщо sequence-діаграма створює Loan у негативному сценарії, вона суперечитиме лабораторній №2.

**Рекомендація AI:** у кожному негативному сценарії явно показати, що запис не створюється.

### Ризик 2 — Плутанина між сутностями та компонентами

Reader, Book і Loan — сутності ER-моделі, а LoanService та репозиторії — програмні компоненти.

**Рекомендація AI:** не представляти репозиторії як нові сутності бази даних.

### Ризик 3 — Неправильні activation bars

Якщо активність LoanService починається до `alt`, її не можна завершувати тільки в одній гілці.

**Рекомендація AI:** завершувати activation bar після `end` комбінованого фрагмента.

## 7. Питання для рішення студента

1. У якому порядку перевіряти читача, книгу та дату повернення?
2. Чи потрібно показувати окремий компонент для отримання поточної дати?
3. Чи використовувати однакових учасників на всіх чотирьох діаграмах?

AI пропонує перевіряти спочатку читача, потім доступність книги, а після цього дату повернення. Це лише пропозиція, яку студент має оцінити перед побудовою діаграм.

## 8. Висновок

Для UC-03 можна створити чотири окремі sequence-діаграми, використовуючи спільні компоненти та різні результати перевірок.

Перед побудовою діаграм потрібно визначити порядок викликів, зберегти відповідність Gherkin-сценаріям та правильно розмістити activation bars.
