# Рішення для Sequence Diagrams

## 1. Що я перевірив

Для лабораторної №3 я вибрав UC-03 «Видача книги» з лабораторної №2.

Після AI-аналізу я переглянув запропонованих учасників, порядок перевірок і можливі помилки в сценаріях.

## 2. Порядок перевірок

Я вибрав такий порядок:

1. Перевірити, чи читач зареєстрований.
2. Перевірити, чи існує книга та чи немає активної видачі.
3. Перевірити дату повернення.
4. Якщо всі умови виконані — створити запис `Loan`.

Такий порядок підходить для всіх чотирьох сценаріїв. Якщо одна з перевірок не пройшла, новий запис `Loan` не створюється.

## 3. Учасники діаграм

Я використовую такі компоненти:

| Учасник | Для чого потрібен |
|---|---|
| Бібліотекар | Починає оформлення видачі |
| `LibraryUI` | Приймає дані та показує результат |
| `LoanService` | Керує перевірками й видачею |
| `ReaderRepository` | Отримує інформацію про `Reader` |
| `BookRepository` | Отримує інформацію про `Book` |
| `LoanRepository` | Перевіряє та зберігає `Loan` |
| `Clock` | Надає поточну дату |

Репозиторії, `LoanService`, `LibraryUI` та `Clock` — це програмні компоненти, а не нові сутності ER-моделі.

## 4. Поточна дата

Я вирішив використовувати окремий компонент `Clock` із викликом `today()`.

Це дозволяє явно показати, звідки система отримує `loan_date`, та перевіряти сценарії з конкретною датою.

## 5. Комбіновані фрагменти

Для всіх чотирьох діаграм використовую `alt`, щоб показати результат перевірки.

- SC-01 — усі перевірки успішні, видачу створено.
- SC-02 — знайдено активну видачу, операцію відхилено.
- SC-03 — дата повернення неправильна, операцію відхилено.
- SC-04 — читача не знайдено, операцію відхилено.

Для повідомлень користувачу можна використати `opt`, якщо це допомагає пояснити окрему необов'язкову дію.

## 6. Що я змінив у пропозиціях AI

AI запропонував використовувати однакову послідовність перевірок для всіх сценаріїв. Я залишив цей варіант, тому що він дозволяє порівнювати діаграми між собою.

Також я вирішив додати `Clock`, щоб не приховувати отримання поточної дати всередині `LoanService`.

Я не додаю нові сутності до ER-моделі та не використовую автоматичні нагадування, оскільки вони не входять до обраного UC.

## 7. Правила для діаграм

- Кожен Gherkin-сценарій має власну sequence-діаграму.
- Кожна діаграма містить щонайменше один `alt` або `opt`.
- Виклики мають зрозумілі назви, наприклад `submitLoan()`, `findReaderById()`, `createLoan()`.
- Показуються повідомлення та відповіді.
- Activation bar у `LoanService` починається перед `alt` і закінчується після нього.
- Негативні сценарії не повинні створювати новий `Loan`.

## 8. Висновок

Для побудови діаграм я використовую спільні компоненти та однаковий порядок перевірок. Це допоможе зберегти відповідність сценаріям із лабораторної №2 і моделі даних із лабораторної №1.
